# Source checks: durable stores and their invariants

One row per file the link (`link/core.ts`, `link/landings.ts`, `link/main.ts`, `link/publish.ts`) or the record keeper
(`record/main.ts`) writes under /data that a tap, an owner line or a card's buttons rest on, then the rest. Columns: who
writes it (and in which function), what is durable before what, what rebuilds it after a restore of the App's state,
what it decides, and the clock behind each time it holds.

Clock rules: whether a tap or an owner line counts is decided only by Discord snowflakes (a message or interaction id),
never by the Pi wall clock: nothing he sends or taps is judged by the Pi's clock. A Pi wall clock use decides only when
something is posted, when a card's buttons come off (through the offset the link measured against Discord's stamps), how
far back to read, or how long something is kept. A bound inside one process runs on the monotonic clock. "fsynced" means
the file (and its folder when the file is new or renamed) is fsynced before the call returns (`applog.ts` appendLog, the
link's `writeDurable`, the link state's store in `publish.ts`, the landing ledger's `writeDurable`, the keeper's
`writeAtomic`). A record in an append-only log is one write under 4000 bytes (`MAX_RECORD_BYTES`), opened for append, so
two writers' records never interleave; a longer one is refused before anything is written.

| Keeper state | /data/record-holds.json | keeper: each round, the recover line | written whole, fsynced, renamed, folder fsynced | the record's holds on GitHub; a missing state is a detected restore and starts degraded; its epoch takes the last status's when that is higher | holds, the rebuild mark, log high-water counts, used recover lines, the generation, the epoch | an item hold lapses after a day on the monotonic clock of this keeper run (from when it saw that renewal) or by the wall clock's idle day, whichever comes first (`holdLapsed`): a lapse only frees an item, so a step of the Pi's clock back can't keep a hold refusing a tap; `alive`, `rebuild.next`, `taps[].at`: Pi wall clock, decides when a rebuild retries and how long an in-state copy of a consumed key is kept (the consumed-key log keeps every key) |
| Keeper's issued-key mirror | /data/record-issued.log | keeper: `mirrorIssued` | each record fsynced | the link's issued-key log | the same as the issued-key log, for a key's whole life | a key ages out by Discord's times (its card snowflake 100 days behind the newest card's); a key without a card snowflake only once a key logged after it in the same file has a card snowflake 100 days behind the newest, never by the Pi's clock |
| Recover file | /data/record-recover.json | link: `recoverLogs` (after his line is judged by Discord's times); keeper: renamed to record-recover.json.taken before acting on it, then deletes only the taken file | written whole, fsynced, renamed, folder fsynced, before "ok"; renamed to its taken name with the folder fsynced before the keeper acts | none | that the keeper rebuilds once (by its message id); a line the link writes while one is taken waits under the link's name and is taken next | `at`: Pi wall clock, decides nothing (the keeper no longer ages it) |

Other files under /data decide nothing about whether a tap or an owner line counts: the relay queue
(/data/relay.queue), the keeper's request queue and outcomes (/data/record-queue, /data/record-outcomes),
the cards view for the reply hook (/data/trust/cards.json, rebuilt from the link state), the Stop state,
Ship key and deploy key (/data/trust), the smoke test's switches (/data/record-block-push,
/data/record-force-conflict, /data/record-clock-test, /data/record-leak-check), the keeper's check-in and
audit files (/data/record-checkin.txt, /data/record-waits.jsonl), and the logs under /data/work.

Monotonic bounds (this process only; the Pi wall clock decides nothing there): the 10-minute replay bound
(`REPLAY_WAIT_MS`, `replayWatch`), the 5-minute wait for verification of a new link run (`VERIFY_PENDING_MS`,
`pendingVerify`), an item hold's day in this keeper run (`holdLapsed`), and the link's keep of a tap record without a
card snowflake (`pruneTaps`). A restart starts each again, so none is ever shorter.

Crash-injection tests (a kill after the write and before its fsync, through `applog.ts` `crashSpy` or the link state
store's crash points; the dependent effect hadn't happened): the issued-key log, the link state (a power-cut model of
the page cache), the held log, the removal queue, the expired-key index, the sweep cursor, the landing ledger, the
consumed-key log, the install log, the keeper status and the recover file. Rows without one: the record trailers and the
source-check ledger (git's own commit), the keeper state (written in the same way as the keeper status, by
`writeAtomic`) and the keeper's issued-key mirror (rebuilt from the link's issued-key log).
