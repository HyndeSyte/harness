# Source checks: durable stores and their invariants

One row per file the link (`link/core.ts`, `link/landings.ts`, `link/main.ts`) or the record keeper
(`record/main.ts`) writes under /data that a tap, an owner line or a card's buttons rest on, then the
rest. Columns: who writes it (and in which function), what is durable before what, what rebuilds it
after a restore of the App's state, what it decides, and the clock behind each time it holds.

Clock rules: whether a tap or an owner line counts is decided only by Discord snowflakes (a message or
interaction id), never by the Pi wall clock. A Pi wall clock use decides only when something is posted,
how far back to read, or how long something is kept. A bound inside one process runs on the monotonic
clock. "fsynced" means the file (and its folder when the file is new or renamed) is fsynced before the
call returns (`applog.ts` appendLog, `writeDurable`, `saveDurable`, the keeper's `writeAtomic`).

| Store | File | Writer | fsync point | Rebuild after a restore | Decides | Clocks |
|---|---|---|---|---|---|---|
| Issued-key log | /data/link-issued.log | link: `runNo` (run), `issueKeys` (key), `armCard` (armed), `voidCard`, `retireUnarmed` (void), `replayWatch` (supersede) | each record appended and fsynced; a card's keys before its state save, its state save before its buttons go on (`issueCard`); a supersede before the line asking him again | none on the link (outside the restorable state); the keeper's mirror /data/record-issued.log; a whole-image restore loses both (the known gap) | which tap keys exist, each key's card, target and expiry, armed, voided or superseded | key expiry as a Discord time: the card's post snowflake plus `life`, a duration fixed once at issuance; `exp` and `at`: Pi wall clock, decides when the sweep takes buttons off and how long a key without a card snowflake is kept |
| Link state | /data/link/state.json | link: `d.save` everywhere | rename; fsynced (`save(s, true)` or `saveDurable`) for the run counter, a card's record before its buttons, a tap's claim before its relay, an owner proposal and its use, an offline line's answer, the verification tuple | its own copy from a backup (older); cards and keys it no longer knows are told as lost from the issued-key log | cards and their outcomes, tap claims, owner proposals (`ownerProposals`, judged by their message snowflakes), `offlineTold`, `verifyChecked`, the run nonce the keeper's verified status must name | proposal and line: Discord snowflakes; `posted`, `expires`, `until`, tap `at`: Pi wall clock, decides when buttons come off and how long a record is kept |
| Held log | /data/link-held.log | link: `holdTap` (held), `releaseHeldTaps` (releasing, released, dropped), `replayWatch` (replay-done) | held fsynced before the card says held; releasing fsynced before the relay | none (outside the restorable state) | which taps are held, and the hold's start (`hold.id`: the hold's first held interaction id) for the keeper's floor | tap time `it` and hold start `hold.id`: Discord snowflakes; `at`: Pi wall clock, decides nothing when `it` is there (a record without one falls back to it) |
| Removal queue | /data/link-strip.log | link: `queueStrip` (strip), `runStrip` (done) | strip fsynced before the edit | none; replayed each sweep until done | which cards lose their buttons; a card in it counts as withdrawn at the arming re-checks | `at`: Pi wall clock, decides nothing |
| Expired-key index | /data/link-expired.log | link: `retireUnarmed`, `sweepPage`, the expiry sweep | each record fsynced before the edit | none | which cards a tap is refused on as expired when the state no longer knows them | `at`: Pi wall clock, decides nothing |
| Sweep cursor | /data/link-sweep.json | link: `saveCursor` | written whole, fsynced, renamed, folder fsynced, after each page | none; a new restore key starts it again | how far back the restore sweep has read, and whether it is done | `before`: a Discord snowflake; the horizon: the start mark's snowflake time less 100 days; done is never written while the Pi wall clock is flagged off (it decides how far to read, never whether) |
| Landing ledger | /data/record-landings/ (and /data/link/landings-marker.json) | link: `landings.ts` claim, settle, settleHand, ownerLine | a claim's file and folder fsynced before the first push; the settle log fsynced before any effect of a hand settle or an owner line | not trusted after a restore until each key is looked for on the remote main | one landing per tap key and per head; each owner line and settle message used once | `at`: Pi wall clock, decides how long a landing is retried (2 hours) and how long a settled key is kept (30 days); giving up only pushes nothing |
| Consumed-key log | /data/record-taps.jsonl | keeper: `appendConsumed` after the tap-derived request's local commit; the rebuild | each record fsynced | the record's `Tap-Key` trailers (local refs and the remote's, after a fresh fetch) and the landing ledger's started claims | which tap keys were acted on (one request per key) | `at`: Pi wall clock, decides nothing |
| Install log | /data/record-install.log | link: `installTaps` (on, once, off); keeper: once-used, off after a restore | each record fsynced before its effect | the record's `Install-Once` trailers; off by default after a restore that lost records | whether Ship taps land | `at`: Pi wall clock, decides nothing |
| Record trailers | the record's git history (`Tap-Key`, `Tap-Request`, `Tap-Card`, `Install-Once`, `Owner-Line`) | keeper: the request's commit | git's commit, then the push | the remote on GitHub | what the rebuild restores into the consumed-key and install logs, and used owner-line codes | commit dates: decide nothing |
| Source-check ledger | the record's state/checks.json | keeper: the `check` op of a request | git's commit, then the push | the remote on GitHub | which source check is accepted for which row version | `checked_at`: the keeper's clock, taken only while its clock verdict says synchronized (a check is refused otherwise); decides how long a check stays fresh (`source_check_max_days`) |
| Keeper status | /data/record-ledger.json | keeper: `writeStatus` each round, `markStart` at once | written whole, fsynced, renamed, folder fsynced | rewritten every round (never restored as truth: a restored one names an older start or link run) | the keeper's start, `verified` (start, link run, fetch count), `verify_pending`, `consumed_unverified`, epoch, tap notices | `verified` is bound to nonces, not times; `clock.at`: Pi wall clock, decides when a tap waits for a synchronized clock; `tap_notices[].at`: decides how long a notice is kept |
| Keeper state | /data/record-holds.json | keeper: each round, the recover line | written whole, fsynced, renamed, folder fsynced | the record's holds on GitHub; a missing state is a detected restore and starts degraded | holds, the rebuild mark, log high-water counts, used recover lines, the generation | `alive`, `rebuild.next`, `taps[].at`: Pi wall clock, decides when holds lapse, when a rebuild retries and how long an in-state copy of a consumed key is kept (the consumed-key log keeps every key) |
| Keeper's issued-key mirror | /data/record-issued.log | keeper: `mirrorIssued` | each record fsynced | the link's issued-key log | the same as the issued-key log, for a key's whole life | a key ages out by Discord's times (its card snowflake 100 days behind the newest card's); `at`: Pi wall clock only for a key without a card snowflake, decides how long it is kept |
| Recover file | /data/record-recover.json | link: `recoverLogs` (after his line is judged by Discord's times); keeper: deletes it once taken | written whole, fsynced, renamed, folder fsynced, before "ok" | none | that the keeper rebuilds once (by its message id) | `at`: Pi wall clock, decides nothing (the keeper no longer ages it) |

Other files under /data decide nothing about whether a tap or an owner line counts: the relay queue
(/data/relay.queue), the keeper's request queue and outcomes (/data/record-queue, /data/record-outcomes),
the cards view for the reply hook (/data/trust/cards.json, rebuilt from the link state), the Stop state,
Ship key and deploy key (/data/trust), the smoke test's switches (/data/record-block-push,
/data/record-force-conflict, /data/record-clock-test, /data/record-leak-check), the keeper's check-in and
audit files (/data/record-checkin.txt, /data/record-waits.jsonl), and the logs under /data/work.

Monotonic bounds (this process only; the Pi wall clock decides nothing there): the 10-minute replay bound
(`REPLAY_WAIT_MS`, `replayWatch`) and the 5-minute wait for verification of a new link run
(`VERIFY_PENDING_MS`, `pendingVerify`). A restart starts each again, so neither is ever shorter.
